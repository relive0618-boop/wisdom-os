# v0.4 Sync Protocol

## Scope and data flow

Scan local reports and cycles, fetch a validated cloud snapshot, canonicalize both payload forms, create a plan, process batches of at most 25, then save safe local metadata. Operations are upload/create/update, download/create/update, conflict or noop. `StoredReport.createdAt` is excluded by the shared payload schema before hashing, so a local-only persistence field never creates a false conflict.

Cloud create, update and soft delete are performed only through `sync_mutate_report` and `sync_mutate_pdca_cycle`. The database derives the owner from `auth.uid()`. Update and soft delete require a positive expected revision in the mutation statement itself; concurrent requests with the same revision permit only one success. Existing active or soft-deleted IDs conflict on create and can never be revived implicitly.

## Error and conflict handling

Each input item produces exactly one safe result. Each successful batch immediately persists its hash and cloud revision; failed or cancelled later batches remain pending for retry. The Migration Wizard persists scan, preview, selection, processed count and errors locally. A user selection controls the exact upload set; cancellation is honoured only between batches.

Conflicts are never overwritten: retain local with the current expected revision, retain cloud only after a local backup, retain both by creating linked new report/cycle IDs with `duplicatedFrom`, or defer without writing anything.

## Security, flags and verification

Only validated payloads, IDs, revisions and canonical hashes travel to the cloud. Feature flags off means no cloud request. Browser roles retain select-only access to private sync tables; authenticated callers receive execute only on the two controlled RPCs. The 20260726 concurrency hardening migration has passed two local zero-state rebuilds and local RPC checks, but has not been applied to Preview. Preview and cross-device verification require a separate approval.
